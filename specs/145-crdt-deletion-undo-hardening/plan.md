# Implementation Plan: CRDT Deletion Error Propagation and Undo Integrity Hardening

**Branch**: `145-crdt-deletion-undo-hardening` | **Date**: 2026-09-17 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/145-crdt-deletion-undo-hardening/spec.md`

## Summary

Harden client-side storage, CRDT lifecycle, deletion failure semantics, and undo integrity:
1. **Propagate Deletion Rejections (P1)**: Stop swallowing errors in `deleteProjectFromDB` and `deleteChapterFromDB`; ensure failures during physical CRDT database deletion reject the parent promise rather than falsely reporting success.
2. **Editor CRDT State Hydration on Undo (P2)**: In `useChapterCRDT`, hydrate the active `Y.Doc` from `crdt_states` snapshot upon opening a chapter, ensuring that undoing a deletion fully restores the collaborative editing lineage and repopulates the dedicated local database.
3. **Snapshot Consistency for Undo (P2)**: In `useProjects.ts`, await pending project writes (`waitForQueueIdle` / `waitForProjectWrites`) before capturing backup snapshots for project and chapter deletion, eliminating race conditions with autosave.
4. **Comprehensive Chapter Discovery (P2)**: Inspect `project.chapters` in `PROJECTS_STORE` in addition to `CHAPTERS_STORE` and `CRDT_STATES_STORE` during project deletion, guaranteeing no dangling physical databases.
5. **Bulk Chapter Deletion Lifecycle (P2)**: Update `deleteChaptersByProjectFromDB` to purge matching records from `CRDT_STATES_STORE` and delete dedicated CRDT databases upon commit.
6. **Relational Foreign-Key Ownership Invariants (P2)**: Enforce that saving a chapter rejects re-parenting across different projects, and saving a CRDT state asserts that the target chapter belongs to the specified `projectId`.
7. **Collision-Safe Persistence Registry & Multi-Instance Cleanup (P2)**: Support multiple active provider instances per database name in `crdtPersistenceRegistry.ts`, and isolate project-scoped provider destruction by explicit project identity instead of naive prefix matching.

## Proposed Changes

### Component 1: Fail-Closed Error Propagation & Chapter Discovery (`src/services/db.ts`)
- In `executeDeleteProjectFromDB`:
  - Inspect `projectsStore.get(id)` to collect chapter IDs from `project.chapters` in addition to `CHAPTERS_STORE` and `CRDT_STATES_STORE`.
  - In `transaction.oncomplete`, call `await deleteProjectCrdtDatabases(id, chapterIdsToDelete)`; reject the promise if an error or timeout occurs instead of swallowing the exception.
- In `deleteChapterFromDB`:
  - In `executeDelete`, call `await deleteChapterCrdtDatabase(resolvedProjectId, id)`; allow exceptions to propagate directly so the operation rejects on failure.
- In `deleteProjectCrdtDatabases`:
  - Also inspect `PROJECTS_STORE` if present to aggregate `project.chapters`.
- In `executeDeleteChaptersByProjectFromDB`:
  - Lock `[CHAPTERS_STORE, CRDT_STATES_STORE]`.
  - Delete records matching `projectId` from both stores.
  - In `transaction.oncomplete`, call `await deleteProjectCrdtDatabases(projectId, deletedChapterIds)`.
- In `executeSaveChapterToDB`:
  - Validate that if the chapter already exists in storage, its `projectId` equals the incoming `projectId`; abort with a warning if mismatched.
- In `executeSaveCrdtState`:
  - Validate that the referenced chapter in `CHAPTERS_STORE` belongs to `record.projectId`; abort with a warning if mismatched.

### Component 2: Multi-Instance & Prefix-Isolated Registry (`src/services/crdtPersistenceRegistry.ts`)
- Change internal tracking from `Map<string, CrdtPersistenceProvider>` to `Map<string, Set<{ provider: CrdtPersistenceProvider; projectId?: string }>>`.
- Support multiple registered providers per `dbName`, and destroy all instances upon `destroyCrdtPersistence(dbName)`.
- Update `destroyAllCrdtPersistencesForProject(projectId, knownChapterIds)`:
  - If `knownChapterIds` is provided, iterate exact names `crdt_${projectId}_${chapId}`.
  - If not provided, inspect registered `projectId` or match exact delimited tokens to prevent `proj_100` from touching `proj_100_200`.

### Component 3: Editor CRDT State Hydration on Open (`src/hooks/useChapterCRDT.ts`)
- When mounting the collaborative editing session:
  - In addition to text hydration fallback, call `getCrdtState(chapterId)`.
  - If a stored CRDT state record exists with a non-empty `update` payload, call `Y.applyUpdate(doc, crdtRecord.update, 'restore-hydration')`.
  - This immediately repopulates the Yjs document state and triggers `IndexeddbPersistence` to persist the update into the dedicated local database.

### Component 4: Serialized Undo Backup Snapshots (`src/hooks/useProjects.ts`)
- In `handleDeleteProject`:
  - Call `await waitForQueueIdle(id)` before reading `getChaptersByProjectFromDB(id)` and `getCrdtStatesByProject(id)`.
- In `handleDeleteChapterHistory`:
  - Call `await waitForQueueIdle(activeProjectId)` before reading `getChapterFromDB(chapId)` and `getCrdtState(chapId)`.

### Component 5: Test Suite Hardening (`src/services/__tests__/projectDeleteQueue.test.ts`)
- Add unit tests verifying that `deleteProjectFromDB` rejects when `deleteDatabase` rejects.
- Add unit tests verifying that `deleteChapterFromDB` rejects when `deleteDatabase` rejects.
- Add unit tests verifying that `project.chapters` is collected during project deletion.
- Add unit tests verifying `deleteChaptersByProjectFromDB` cleans up CRDT states and databases.
- Add unit tests verifying foreign-key ownership checks in `saveChapterToDB` and `saveCrdtState`.
- Add unit tests for multi-instance persistence registry and prefix isolation.
